3. JWT Authentication
Step-by-Step Auth Flow
Signup Flow
POST /auth/register → validate fields → bcrypt.hash(password, 10) → generate custom userId = CFT_user_${randomHex}_${timestampBase36}_ → create User doc with isVerified: false
Generate a verification JWT: jwt.sign({ email, jti: randomHex }, JWT_SECRET, { expiresIn: '10m' }) — this is the one embedded in the email link, not the session token
Send Brevo email with link: FRONTEND_URL/verify-email/<verificationToken>
User clicks link → GET /auth/verify-email/:token → jwt.verify(token, JWT_SECRET) → set isVerified: true, clear verificationToken field from DB, send welcome email
Login Flow
POST /auth/login (CSRF-protected)
Check Redis for login:attempts:<email> — if ≥ 5, return 429
If there's an existing cookie token, blacklist it in Redis before continuing (prevents double-sessions)
Find user by email (checks Redis cache user:login:<email> first for speed)
bcrypt.compare(password, user.passwordHash) — fails → increment attempt count → return generic "Invalid credentials" (prevents user enumeration)
Check user.isVerified — false → 403
Clear failed attempt counter from Redis
Generate session JWT: jwt.sign({ userId: user.userId, jti: randomHex }, JWT_SECRET, { expiresIn: '3d' })
Note: payload uses custom userId (e.g. CFT_user_abc123_...), NOT MongoDB's _id
Set httpOnly cookie: res.cookie('token', token, { httpOnly: true, secure: isProd, sameSite: 'Strict', domain: '.carbonft.app', maxAge: 3d })
If first-time local user (!welcomeEmailSent), send welcome email asynchronously with setImmediate()
Return { message: 'Login successful', user: { name } } — no token in JSON, only in cookie
Where is the JWT Stored?
httpOnly cookie named token. It cannot be read by JavaScript at all. On every subsequent request the browser automatically sends it. The backend reads it at 
authmiddleware.js:L10
: req.cookies?.token.

There is also a fallback to Authorization: Bearer <token> header at 
authmiddleware.js:L13-15
 (for non-browser clients).

Protected Route Middleware — authenticateToken
File: 
middleware/authmiddleware.js

The middleware runs 4 checks in sequence:


Step 1: Extract token from cookie (or Authorization header fallback)
         → No token → 401 "Access denied"
Step 2: jwt.verify(token, JWT_SECRET)
         → invalid signature / expired → 401 (clears cookie)
Step 3: Check Redis key blacklist:jti:<decoded.jti>
         → exists → 401 "Session expired" (clears cookie)
         This is how logout actually invalidates tokens before natural expiry!
Step 4: User exists check:
         → Try Redis cache key user:auth:<userId> (10 min TTL)
         → If cache miss, query MongoDB User.findOne({ userId })
         → User not found → 401 (clears cookie)
If all pass: req.user = { userId, jti }  →  next()
The JTI (JWT ID) is a crypto.randomBytes(16).toString('hex') unique per token. This is what makes blacklisting work — you don't need to store every valid token, only the revoked ones.

Token Expiry & No Refresh Token (on Login Route)
The login route issues a single 3-day JWT. There is no refresh token mechanism on the login route (the generateTokens() function in 
auth.js:L282-299
 that generates access + refresh tokens exists in the code but is not currently used in the login route — the login route does its own jwt.sign directly). When the 3-day token expires, the middleware returns TokenExpiredError → 401, and the frontend redirects to /login.

For Google OAuth: same pattern — a 3-day JWT cookie is set in the /google/callback handler at

5. MongoDB & Data Modeling
User Schema — models/user.js
js

{
  userId:            String  (required, unique, indexed) — custom ID like "CFT_user_abc_1xyz_"
  name:              String  (required)
  email:             String  (required, unique index)
  provider:          String  enum: ['local', 'google']  default: 'local'
  passwordHash:      String  (not required — Google users have no password)
  isVerified:        Boolean default: false
  verificationToken: String  (cleared after verification)
  resendAttempts:    Number  default: 0  (tracks resend email count)
  lastResendAt:      Number  (Unix ms timestamp)
  welcomeEmailSent:  Boolean default: false
  feedbackGiven:     Boolean default: false
  timestamps: true   → createdAt, updatedAt auto-managed by Mongoose
}
Why custom userId instead of MongoDB _id? Because _id is a MongoDB ObjectId and exposing it in JWTs or URLs is a security anti-pattern. The custom userId is opaque, non-sequential, and not predictable.

TTL index on unverified users:

js

userSchema.index({ lastResendAt: 1 }, {
  expireAfterSeconds: 600,
  partialFilterExpression: { isVerified: false }
})
This tells MongoDB to automatically delete unverified accounts 10 minutes after their last resend. This keeps the DB clean of abandoned registrations.

CarbonEntry Schema — models/CarbonEntry.js
js

{
  userId: String (required, unique, indexed, sparse) — foreign key to User.userId
  entries: [          ← EMBEDDED ARRAY — all entries in one document per user
    {
      food: {
        type:     String enum: ['Animal based', 'Plant based', 'Both']
        amountKg: Number
      },
      transport: [{
        mode:       String enum: ['Car', 'Bike', 'Bus', 'Metro', 'Walking', 'Train', 'Flights']
        distanceKm: Number
      }],                 ← Array (user can log multiple transport modes)
      electricity: [{
        consumptionKwh: Number
        source:         String enum: ['Coal', 'Solar', 'Wind', 'Hydro', 'Mixed']
      }],
      waste: [{
        plasticKg:   Number  default: 0
        paperKg:     Number  default: 0
        foodWasteKg: Number  default: 0
      }],
      createdAt: Date
      updatedAt: Date
    }
  ]
}
Compound index: { userId: 1, 'entries.createdAt': -1 } — speeds up time-sorted queries per user.

Collection Relationship
There are two collections: users and carbonentries.

The link is: CarbonEntry.userId === User.userId (string-to-string reference, not a Mongoose ObjectId ref/populate). This is a manual reference — you join them yourself, like in the leaderboard route at 
footprint.js:L131-133
:

js

for (const user of allUsers) {
  const carbonEntry = await CarbonEntry.findOne({ userId: user.userId }).lean();
  // manual join!
}
Why embed entries instead of a separate collection? All entries for a user are always queried together. Embedding avoids expensive joins and keeps the query simple: one findOne({ userId }) gets everything. The trade-off is document size, which is managed by the $slice aggregation to only return 5 entries.

5 Likely Interview Questions — With Your Actual Answers
Q1: Why did you store the JWT in a cookie instead of localStorage?

Point to: 
routes/auth.js:L531-538

How to answer: "localStorage is vulnerable to XSS — any injected script can read it. I set the cookie with httpOnly: true, which means JavaScript on the page has zero access to it. Combined with sameSite: 'Strict' it also blocks CSRF from third-party sites. To add another layer, I added csurf CSRF tokens on the server for all state-changing operations, since cookies alone aren't enough when frontend and backend are on different subdomains."

Q2: You have no refresh token — how do you handle token expiry?

Point to: 
middleware/authmiddleware.js:L143-145
, 
routes/auth.js:L524-526

How to answer: "The session token has a 3-day expiry. On expiry, jwt.verify() throws TokenExpiredError, the middleware returns 401, and the Axios interceptor in the frontend detects requiresLogin: true in the response and hard-redirects to /login. For longer sessions I could implement refresh tokens — I actually wrote the generateTokens() function at line 282 of auth.js that creates both an access token (10 min) and refresh token (14 days), but the current login route uses a single 3-day token for simplicity. It's ready to be wired up."

Q3: Explain your MongoDB data model — why are entries embedded in a single document instead of a separate collection?

Point to: 
models/CarbonEntry.js
, 
routes/footprint.js:L27-42

How to answer: "I used MongoDB's embedded document pattern. Each user has one CarbonEntry document with an entries array. When I add an entry I use $push, when I delete I use $pull, when I update I use the positional $ operator. This avoids a separate collection join every time I need all of a user's data. The trade-off is document size, but I handle that by always querying with $slice in an aggregation to return only the 5 most recent entries at the database level — not in the application layer. I also created a compound index on { userId: 1, 'entries.createdAt': -1 } for performance."

Q4: How does your logout actually invalidate the JWT before it naturally expires?

Point to: 
routes/auth.js:L588-627
, 
middleware/authmiddleware.js:L41-60

How to answer: "JWTs are stateless — you can't 'delete' one. The standard approach is to let it expire naturally, but that's a security hole if someone logs out on a shared computer. My solution: every JWT has a jti field — a unique ID generated with crypto.randomBytes(16). On logout, I calculate the token's remaining TTL (decoded.exp - Date.now()/1000) and store blacklist:jti:<jti> in Redis with that exact TTL. The auth middleware checks Redis for this key on every request — if it finds it, the token is rejected. When the JWT would have expired anyway, Redis also expires the key, so no memory leak. I even blacklist the old token during a new login if a cookie already exists."

Q5: Walk me through how the weather feature avoids hammering the API on every page load.

Point to: 
routes/auth.js:L1140-1181

How to answer: "The weather endpoint uses a multi-layer strategy. First, coordinates are rounded to 2 decimal places (Math.round(lat * 100) / 100) so nearby locations share the same cache key. Second, I check Redis for weather:<lat>,<lon> — if the cache exists and it's not a ?refresh=true request, I return the cached data immediately. If the cache TTL drops below 5 minutes, I serve the stale data to the user right away but trigger a background refresh with setImmediate() — this is stale-while-revalidate. If it's a fresh fetch, I try Tomorrow.io first, then Weatherbit, then Open-Meteo in a try-catch chain. Whatever succeeds gets cached for 30 minutes. I also have Redis-based rate limiting on how many times a user can force-refresh."
